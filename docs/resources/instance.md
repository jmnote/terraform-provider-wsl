# wsl_instance (Resource)

Manages a WSL instance's registration lifecycle, an in-place WSL-version update, and delete via `wsl --unregister`. It does not manage anything inside the instance. Creation supports two mutually exclusive modes: install a Microsoft Store distribution with no tar file at all via `distribution` (`wsl --install`) -- the same primitive everyday, interactive `wsl --install <Distribution>` uses -- or bring your own root filesystem tar via `rootfs`+`location` (`wsl --import`). See docs/design/decisions/creation-model.md for why both exist and the constraints of each.

~> **Destructive delete.** `terraform destroy`, or any change to `name`, `distribution`, `rootfs`, or `location`, unregisters the instance via `wsl --unregister`, which permanently deletes its virtual disk and all data inside it. There is no undo and this provider does not take backups.

## Example Usage

### Install mode (Microsoft Store distribution, no tar needed)

```terraform
# Install mode: no rootfs tar needed. name is always required -- see
# docs/design/decisions/required-name.md for why this provider does not
# default it to distribution the way wsl.exe itself does.
resource "wsl_instance" "ubuntu" {
  name         = "ubuntu"
  distribution = "Ubuntu-24.04"
}
```

Valid values for `distribution` come from WSL's own distribution catalog
(`wsl --list --online`, backed by
[`DistributionInfo.json`](https://github.com/microsoft/WSL/blob/master/distributions/DistributionInfo.json)
in the `microsoft/WSL` repository). A bare flavor name like `"Ubuntu"`
floats to whichever entry that flavor's catalog currently marks
`Default: true`; a specific entry name like `"Ubuntu-24.04"` pins to that
one.

### Multiple instances from the same distribution

```terraform
# Multiple instances can be stamped out from the same Store distribution,
# each under its own name.
resource "wsl_instance" "debian1" {
  name         = "debian1"
  distribution = "Debian"
}

resource "wsl_instance" "debian2" {
  name         = "debian2"
  distribution = "Debian"
}
```

### Import mode (bring your own rootfs tar, or a `.wsl` file)

```terraform
resource "wsl_instance" "debian3" {
  name     = "debian3"
  rootfs   = "C:\\images\\debian-12.tar"
  location = "D:\\WSL\\debian3"
  version  = 2
}
```

A `.wsl` file (the packaging format `wsl --install --from-file` and the
Microsoft Store both use -- it's a tar archive with a `.wsl` extension;
see [Microsoft's custom distro guide](https://learn.microsoft.com/en-us/windows/wsl/build-custom-distro))
works as `rootfs` here too: `wsl --import` accepts it exactly like a plain
`.tar`/`.tar.gz`, with no separate attribute needed for it.

## Schema

### Required

- `name` (String) The instance's registration name, e.g. "Ubuntu-24.04". This is also the identity used by `terraform import`. Changing it requires replacing the resource: WSL has no rename operation. Always required, including in install mode: silently defaulting an omitted name to `distribution` (as wsl.exe itself does when `--name` is not passed to `wsl --install`) would risk colliding with an unrelated, already-registered instance of that name that you did not intend to touch.

### Optional

- `distribution` (String) Install mode: a Microsoft Store distribution identifier (e.g. "Ubuntu-24.04") to stamp this instance out from, installed via `wsl --install` with no tar file needed and no other registered instance touched. Required in install mode; mutually exclusive with `rootfs`/`location`. Run `wsl --list --online` to see valid values. A bare flavor name (e.g. "Ubuntu") floats to whatever that flavor's catalog entry currently marks as default and can resolve to different content over time as Microsoft updates the catalog; a specific name (e.g. "Ubuntu-24.04") pins to that entry. Multiple instances can be stamped out from the same distribution under different `name`s.
- `location` (String) Import mode: Windows directory where WSL stores the instance's virtual disk (the `wsl --import` install location). Required together with `rootfs`; mutually exclusive with `distribution`. Like `rootfs`, WSL exposes no way to read this back for an existing instance, so after `terraform import` this remains unset in state until your configuration supplies it.
- `rootfs` (String) Import mode: path to the tar/tar.gz root filesystem archive to import (the `wsl --import` source). Required together with `location` when creating an import-mode resource; mutually exclusive with `distribution`. WSL exposes no way to read this back for an existing instance, so after `terraform import` this remains unset in state until your configuration supplies it.
- `version` (Number) WSL engine version the instance runs under: 1 or 2. Changing this performs an in-place `wsl --set-version` rather than replacing the resource, since Microsoft documents that as a supported (if potentially slow) conversion.

### Read-Only

- `state` (String) The instance's current run state (e.g. "Running"/"Stopped") as last observed from `wsl --list --verbose`. Informational only: on a non-English Windows host this text is localized, so it must not be relied on programmatically.

## Import

Import uses the instance's registration name as the entire import ID:

```shell
terraform import wsl_instance.debian3 debian3
```

Because WSL exposes no way to read back the original `distribution`,
`rootfs`, or `location`, those attributes are left unset by import. Write
matching values into your configuration before the next `terraform plan`;
see [design/decisions/observable-state.md](https://github.com/jmnote/terraform-provider-wsl/blob/main/docs/design/decisions/observable-state.md)
for why, and how the schema avoids proposing a destructive replace on that
first plan.
